# 10 — Level 2: Monte Carlo and 3D rendering (sampling audits)

**Status: testnet, not audited.** This document describes what is implemented (`vearl-core/src/l2.rs`), its byte-by-byte specification (for a second implementer), and — above all — **what this level does and does not guarantee**.

## 1. Honest positioning

Level 1 (matrix products, tensor programs) is **exactly verifiable at almost no cost** (Freivalds, single-entry fraud proofs) and its work is **also the consensus work** (the miner computes the client's GEMM). Level 2 has neither of these properties:

| | level 1 | level 2 |
|---|---|---|
| link with consensus | the client's computation *is* the mined work | **none**: a service paid at full cost (escrow, bond, burning), no *rebate* |
| verification | exact: a wrong entry is **always** provable | **by sampling**: only the chunks actually recomputed are checked |
| guarantee | "if Accept, the result is exact" (error probability ≤ 2⁻²⁴) | "if Accept after m checks on N chunks, an isolated falsification passes unnoticed with probability 1 − m/N" |

Level 2 therefore does **not** claim that the complete result is exact; it makes cheating **risky and sanctioned**, with a detection probability that the client sets through the number of chunks it recomputes.

## 2. Model: deterministic chunks, Merkle commitment, one-chunk proof

- A job is a **kernel frozen by the protocol** (Monte Carlo or rendering) plus **public, on-chain** parameters (small: ≤ 64 instructions, ≤ 8 primitives), and a number of `chunks` (≤ 1024). No arbitrary client code is executed: no sandbox needed.
- Each chunk `i` is a **deterministic** function `kernel(parameters, i) → bytes` (≤ 4096 bytes), in **integers only** (no floating point: results are identical on any hardware).
- The worker publishes `root` = Merkle root (§3 of `docs/07`) of the leaves `leaf_hash(i, output_i)`, depth `⌈log2 chunks⌉`. **It publishes no output on-chain**: only the root.
- **Fraud proof**: `Fraud{job, chunk, out, path}` — `out` must be opened against `root` at index `chunk`; the chain **recomputes that single chunk** (bounded cost, see §5); if the result differs from `out` → the worker is sanctioned (half of the bond to the reporter, half burned, the client is refunded).
- **Availability**: the client can demand on-chain the output of a chunk (`Fetch`, retained fee); the worker answers with `Serve` (Merkle opening) within `serve_secs`, otherwise `SlashUnserved`. Off-chain, the worker also serves the chunks over the network (`GetL2Chunk`).
- **Settlement**: `Accept` by the client, or `Settle` by anyone once the challenge window (blocks **and** seconds) has elapsed.

## 3. Monte Carlo kernel (specification)

Parameters `McParams{seed [32], dim u8 (1..=8), samples u32 (1..=4096), out u8 (<16), program Vec<Instr>}`; `Instr{op u8, a u8, b u8, c u8, imm i64}`, 1 to 64 instructions.

**Draws**: `stream = XOF("vearl/l2/mc/v1", seed || chunk u32 LE, samples·dim·4 bytes)` (BLAKE3 in `derive_key` mode, §1 of `docs/07`); input `b` of sample `k` is the LE `u32` word of index `k·dim + b`, interpreted as the integer `x ∈ [0, 2³²)`, i.e. the fraction `x/2³²` in **Q32** fixed point.

**Machine**: 16 `i64` registers (Q32) reset to 0 for each sample; the program runs in order. `sat(v)` = saturation into `i64`. Operations:
`0 LDC a,imm: r[a]=imm` · `1 INP a,b: r[a]=input b (b<dim)` · `2 ADD` · `3 SUB` (saturated) · `4 MUL a,b,c: r[a]=sat((r[b]·r[c]) >> 32)` (exact 128-bit product, arithmetic shift = rounding toward −∞) · `5 MIN` · `6 MAX` · `7 ABS a,b` · `8 NEG a,b` (saturated) · `9 SQRT a,b: r[a]=⌊√(max(r[b],0)·2³²)⌋` (exact integer square root) · `10 LT a,b,c: r[a] = (r[b]<r[c]) ? 2³² : 0` · `11 SEL a,b,c,imm: r[a] = (r[b]>0) ? r[c] : r[imm & 15]`. Registers and `b<dim` are validated at submission.

**Chunk output** (32 bytes): `Σ v` (signed 128-bit integer, LE) `||` `Σ ((v·v) >> 32)` (likewise), where `v = r[out]` after the program, summed over the `samples` samples. The client derives the mean and the standard error from it (`E[v²] − E[v]²`).

Example: `mc_pi_program` (indicator of the quarter disc) → `E = π/4`; measured: `π ≈ 3.14497` with 262,144 samples.

## 4. Rendering kernel (specification)

Parameters `RenderParams{seed [32], width u16, height u16, spp u8 (1..=4), cam_z i32, light [i32;3], prims Vec<Prim> (1..=8)}` — width and height multiples of 16, ≤ 512; `i32` coordinates in **Q16.16** fixed point (`|v| ≤ 2²⁴`). `Prim`: `Sphere{c[3], r>0, col[3] u8}`, `Plane{y, col, col2}` (checkerboard of 1.0 cells), `Box{c[3], h[3]>0, col}`. Number of chunks = `(width/16)·(height/16)` (one 16×16 tile per chunk; chunk `i` → tile `(i mod tx, ⌊i/tx⌋)`). Output: 768 bytes, RGB per pixel, row by row.

Constants: `Q = 2¹⁶`; `MARCH_STEPS = 48`, `SHADOW_STEPS = 24`, `HIT_EPS = 64`, `T_MAX = 20·Q`; `mul16(a,b) = (a·b) >> 16` (arithmetic); `len3(v) = ⌊√(x²+y²+z²)⌋`; `norm3(v)` = each component `(c << 16) / len3` (division **truncated toward zero**), and `(0, Q, 0)` if the length is zero; `at(o,d,t) = o + mul16(d, t)`.

For the tile's pixel `(x, y)` and sample `s`: if `spp = 1` the sub-pixel offset is `(32768, 32768)`; otherwise `(jx, jy)` = two LE `u16` at offset `((y·16 + x)·spp + s)·4` of `XOF("vearl/l2/render/v1", seed || chunk u32 LE, 16·16·spp·4)`. With `sx = px·Q + jx`, `sy = py·Q + jy` (absolute pixel): `u = (2·sx − W·Q) / W`, `v = −((2·sy − H·Q) / W)` (divisions truncated toward zero), direction `d = norm3(u, v, Q)`, origin `o = (0, 0, −cam_z)`, light `L = norm3(light)`.

**Distance** `sdf(p)` = minimum over the primitives (tie → lowest index): sphere `len3(p − c) − r`; plane `p.y − y`; box `len3(max(q,0)) + min(max(q.x,q.y,q.z), 0)` with `q = |p − c| − h`.
**March**: `t = 0`; up to 48 times: `pos = at(o,d,t)`, `(dist, k) = sdf(pos)`; if `dist < 64` → hit (primitive `k`); otherwise `t += dist`, and stop if `t > T_MAX`. No hit: `c_i = 20 + ((sky_i · (d.y + Q)) >> 17)` with `sky = (90, 120, 180)`.
**Lighting**: normal = `norm3` of the central differences of `sdf` at step `256`; `diffuse = max((n·L) >> 16, 0)`; shadow: march toward `L` from `pos + mul16(n, 1310)` (24 steps, same rule, stop at `T_MAX/2`); `shade = Q` if lit otherwise `Q/4`; `inten = min(13107 + mul16(52429, mul16(diffuse, shade)), Q)`; base colour: `col` (plane: `col` if `(⌊pos.x/Q⌋ + ⌊pos.z/Q⌋)` is even, otherwise `col2`, with `⌊·⌋` = arithmetic shift); channel = `(base · inten) >> 16`. The pixel averages the `spp` samples by integer division.

## 4 bis. Render2: a cinematic GPU renderer (specification)

`Kernel::Render2` (`u32` tag 2, appended after `MonteCarlo` 0 and `Render` 1) is a second rendering kernel. It keeps the properties that make level 2 judgeable (integers only, one deterministic 16×16 tile per chunk) and adds what makes an image look finished: **smooth blending of shapes, soft shadows, ambient occlusion, up to two mirror bounces with a Fresnel term, emissive glow and neon light on nearby surfaces, fog, a procedural sky with a sun and stars, a free camera, ACES tone mapping and a vignette**. Reference code: `vearl-core/src/render2.rs`; independent implementation: `tools/l2_ref.py` (`render2_chunk`); GPU port: `gpu/vearl_render2.cu`. All three give the same 768 bytes for every tile (`tests/gpu.rs::gpu_render2_tiles_equal_the_cpu_reference`, `tools/l2_ref.py` on the frozen vectors).

**Parameters** `RenderParams2{seed [32], width u16, height u16, spp u8 (1..=4), bounces u8 (0..=2), cam [i32;3], target [i32;3], fov i32, light [i32;3], light_col [u8;3], sky_top [u8;3], sky_hor [u8;3], fog i32, smooth_k i32, exposure i32, prims Vec<Prim2> (1..=16)}`; `Prim2{shape, mat}`; `Material{col [u8;3], col2 [u8;3], refl u8, emit u8, checker bool}`; `Shape` = `Sphere{c, r}` · `Box{c, h, rnd}` · `Torus{c, big, small}` · `Plane{y}` (bincode tags 0..3 in this order). Width and height are multiples of 16, at most 2048; chunk count = `(width/16)·(height/16)`, at most `MAX_RENDER_CHUNKS = 8192` (a 1920×1088 frame has 8,160). Coordinates are Q16.16 (`|v| ≤ 2²³`), `fov ∈ [Q/4, 8Q]` (Q = 65536 = a 90° horizontal field of view; larger = narrower), `fog ≤ 8Q`, `smooth_k ≤ 4Q`, `exposure ≤ 16Q`, radii and half sizes positive, `big > small > 0`. Validation is `render2_validate`.

**Notation.** All values are `i64`; `Q = 65536`; `mul16(a,b) = (a·b) >> 16` (arithmetic shift); `/` truncates toward zero; `isqrt` is the exact integer square root; `len3`, `norm3` (null vector → `(0,Q,0)`), `dot16(a,b) = (Σ aᵢbᵢ) >> 16`, `cross16(a,b)ᵢ = (aⱼbₖ − aₖbⱼ) >> 16`, `at(o,d,t) = o + mul16(d,t)` as in §4. A colour channel `c ∈ 0..255` becomes linear with `lin(c) = (c²·65536) / 65025`. `pow_sq(x, n)` squares `x` n times with `mul16`.

**Distance field.** `shape_dist`: sphere `len3(p−c) − r`; plane `p.y − y`; rounded box `len3(max(q,0)) + min(max(qx,qy,qz),0) − rnd` with `q = |p−c| − h`; torus (axis `y`) `len2(len2(qx,qz) − big, qy) − small` with `q = p − c`. The scene distance is `min(blend, plane)`: `blend` folds the non-plane shapes in index order with `smin(a,b,k) = min(a,b) − ((mul16(hq,hq)·k) >> 18)` where `h = max(k − |a−b|, 0)`, `hq = (h<<16)/k` (`smin = min` when `k = 0`), and `plane` is the minimum over the planes. The **nearest shape** is the lowest index with the smallest raw distance; the **nearest emissive shape** (`emit > 0`) is defined the same way over the emissive shapes.

**Camera.** `fwd = norm3(target − cam)`, `right = norm3(cross16((0,Q,0), fwd))`, `up = norm3(cross16(fwd, right))`. For pixel `(px,py)` and sample offset `(jx,jy)` (`(32768,32768)` when `spp = 1`, otherwise two LE `u16` of the XOF of §4 at offset `((y·16+x)·spp+s)·4`): `sx = px·Q + jx`, `sy = py·Q + jy`, `u = (2sx − W·Q)/W`, `v = −((2sy − H·Q)/W)`, ray direction `norm3(mul16(fwd,fov) + mul16(right,u) + mul16(up,v))` from `cam`.

**Constants.** `MARCH = 64`, `HIT_EPS = 64`, `T_MAX = 40Q`, `FAR_HIT = 8192`, `SOFT_STEPS = 32`, soft-shadow start `2621`, `SOFT_T_MAX = 14Q`, normal step `256`, surface offset `BIAS = 2621`, `GLOW_R = 3Q/5`, `EMIT_LIGHT_R = 5Q/2`, `AO` steps `5243·i` (i = 1..5) with weights `65536, 62259, 59146, 56188, 53379`, gains `DIRECT 2`, `SPEC 2`, `AMBIENT 2`, `EMIT_LIGHT 3`, `VIGNETTE 22000`, ACES coefficients `164495, 1966, 159252, 38666, 9175`.

**Sky** `sky(d)`: `e = clamp(5·d.y, 0, Q)`, `m = mul16(e, 2Q − e)`; sun `s = max(dot16(d, L), 0)` with `L = norm3(light)`, `s64 = pow_sq(s,6)`, `s256 = pow_sq(s64,2)`, `sun = (s64 >> 2) + (s256 << 2)`; stars: if `d.y > 0`, `h = star_hash((d.x>>6) as u32, (d.y>>6) as u32, (d.z>>6) as u32)` (`h = x·0x9E3779B1 ⊕ y·0x85EBCA77 ⊕ z·0xC2B2AE3D` mod 2³², `h ⊕= h>>15`, `h = h·0x2C1B3C6D`, result `h ⊕ (h>>12)`) and, when `h & 0x1FFF = 0`, `star = mul16(((h>>13)&0xFF) << 8, Q − m)·2`, otherwise 0. Channel `i`: `hor_i + mul16(top_i − hor_i, m) + mul16(light_i, sun) + star` (all linear colours).

**Surface shading** at a hit point `pos` of shape `k`, ray direction `d`, ray length `t`: `n = norm3` of the central differences of the scene distance (step 256); base colour `lin(col)` (plane with `checker`: `col` when `((pos.x>>16) + (pos.z>>16))` is even, `col2` otherwise); `ndl = max(dot16(n,L),0)`; **soft shadow** from `o = pos + mul16(n,BIAS)` along `L`: `res = Q`, `t₀ = 2621`; up to 32 steps: `d = dist(o + L·t₀)`; `d < HIT_EPS` → `res = 0`, stop; else `res = min(res, ((8d)<<16)/t₀)`, `t₀ += clamp(d, 1311, 32768)`, stop above `14Q`; then `r = clamp(res,0,Q)` and `shadow = mul16(r, mul16(r, 3Q − 2r))`. **Occlusion**: `occ = Σ (max(hr − dist(pos + mul16(n,hr)), 0)·w_i) >> 16` with `hr = 5243·i`; `ao = clamp(Q − (occ + (occ >> 1)), 0, Q)`. `hemi = clamp((n.y+Q)>>1, 0, Q)`; `half = norm3(L − d)`; `spec = pow_sq(max(dot16(n,half),0), 5)`. **Neon light**: from the nearest emissive shape at `pos` with distance `ed`, if `ed < 5Q/2`: `w = ((5Q/2 − max(ed,0))<<16)/(5Q/2)`, `ew = mul16(w,w)`, colour `lin(col)` of that shape. **Fog**: `f = clamp(mul16(t, fog), 0, Q)`, `fogf = mul16(f,f)`, fog colour `sky(d)` (only evaluated when `fogf > 0`). Channel `i`: `amb = mul16(hor_i + mul16(top_i − hor_i, hemi), ao)·2`, `direct = mul16(light_i, mul16(ndl, shadow))·2`, `spec_c = mul16(light_i, mul16(spec, shadow))·2`, `col = mul16(base_i, direct + amb + mul16(ecol_i, ew)·3) + spec_c + mul16(base_i, emit·512)`, result `col + mul16(sky_i − col, fogf)`.

**Ray tracing** `trace(o, d)` accumulates linear HDR light `acc` with a throughput `thr = Q`; for `bounce` in `0..=bounces`: march at most 64 steps (`t += dist`, hit when `dist < HIT_EPS`, miss when `t > T_MAX`); if the 64 steps ran out without leaving the scene and the last distance was `< FAR_HIT`, the last point counts as a hit (grazing floors; the fog hides it); during bounce 0 the glow is added: for the nearest **non-sphere** emissive shape seen along the march (smallest distance `gmin`), if `gmin < GLOW_R`: `g = ((GLOW_R − max(gmin,0))<<16)/GLOW_R`, `acc += mul16(lin(col_e), mul16(g,g)) >> 1`; and, for **every emissive sphere** (exact, no sampling), with `oc = centre − o`, `tc = clamp(dot16(oc, d), 0, t_end)` (`t_end` = the hit distance, or `T_MAX` for a miss), `dist = len3(o + mul16(d, tc) − centre) − r`, the same term with `dist` in place of `gmin`; a miss adds `mul16(thr, sky(d))` and stops; a hit computes the surface colour; with `refl = refl_u8·257`, if this is the last bounce or `refl = 0`: `acc += mul16(thr, colour)`, stop; otherwise Fresnel `f = min(refl + mul16(Q − refl, pow5(Q − clamp(dot16(−d,n),0,Q))), Q)` (`pow5(x) = mul16(mul16(x²,x²),x)`), `acc += mul16(thr, mul16(colour, Q − f))`, `thr = mul16(thr, f)`, reflect `d = norm3(d − 2·mul16(dot16(d,n), n))`, `o = pos + mul16(n, BIAS)`.

**Pixel output.** The `spp` HDR samples are averaged (`acc/spp`), multiplied by `exposure` and by the vignette `vig = max(Q − mul16(mul16(nx,nx) + mul16(ny,ny), 22000), 16384)` (`nx = (2cx − W·Q)/W`, `ny = (2cy − H·Q)/W` at the pixel centre `c = p·Q + Q/2`), tone-mapped with an ACES approximation: `num = mul16(c, mul16(A,c) + B)`, `den = mul16(c, mul16(C,c) + D) + E`, `aces = clamp((num<<16)/den, 0, Q)`, and gamma-encoded with `byte = min(isqrt((aces·65025) >> 16), 255)`.

**Cost bound.** One tile costs at most `256 · spp · (1 + bounces) · (MARCH + 7 + SOFT_STEPS + AO_N) · shapes` evaluation units (`render2_cost`), at most 5.3 M for the largest legal setting (spp 4, 2 bounces, 16 shapes), under `MAX_CHUNK_COST = 8,000,000`: the recomputation of one tile by a judge stays bounded (a few tens of milliseconds on a CPU core).

**What the GPU changes, and what it does not.** On a `--gpu` worker the whole image is computed by `vearl_gpu_render2` (one CUDA block per tile, one thread per pixel); every integer operation is the same as on the CPU, so the Merkle root of the chunk outputs is identical and a node without a GPU judges a fraud proof by recomputing that single tile on its CPU. The level-2 guarantee is unchanged (§1): a sampling audit, not an exact proof. Measured on an RTX 5060 Ti: see §8.

## 4 ter. Render3: a path tracer for production-quality images (specification)

`Kernel::Render3` (`u32` tag 3, appended after `Render2`) is the protocol's production renderer. Render2 (§4 bis) is the instant preview; Render3 is a **Monte Carlo path tracer over signed distance fields** that follows the same method as the offline renderers used for studio product shots: global illumination by random walks with up to 14 bounces, glass with refraction, Fresnel and Beer absorption, rough metals (GGX), clear coat, thin translucency, emission, a studio environment made of soft boxes, a thin-lens camera (depth of field with round bokeh), distance fog, procedural textures with bump mapping, and a rich set of shapes. **Everything is integer arithmetic**: the 1,536 output bytes of a chunk are bit-identical on every CPU and on the GPU (`gpu/vearl_render3.cu`), so a node judges a one-chunk fraud proof by recomputing that chunk. Reference code: `vearl-core/src/render3.rs`; independent implementation: `tools/l2_ref.py` (`render3_chunk`); frozen vectors: cases `render3` of `tests/vectors/l2-kernels-v1.json`; GPU equality test: `tests/gpu.rs::gpu_render3_chunks_equal_the_cpu_reference` (including the complete watch scene).

**Chunks and passes.** A job renders a `width × height` image (multiples of 16, at most 2048) as `passes` independent passes. **One chunk = one pass of one 16×16 tile**: `chunk = pass · tiles + tile`, `tile = ty · (width/16) + tx`, `chunks = tiles · passes ≤ MAX_CHUNKS3 = 262,144`. A pass takes `spp ≤ 32` samples per pixel and `bounces ≤ 14`. The chunk output is **1,536 bytes** (256 pixels × 3 channels × 2 bytes): per pixel, three little-endian `u16` holding the **mean radiance of the pass's samples in Q11** (2048 = 1.0, each sample capped at 24.0 before averaging, the mean capped at 32.0). The final picture is the per-tile average of the passes, then exposure, ACES, vignette and gamma; this assembly is off-chain (`render3::assemble`) and not a consensus rule. The first pass of a tile does not depend on the number of passes, so a render can be extended with more passes.

**Cost bound.** One chunk costs at most `256 · spp · (bounces + 1) · (MARCH + 8) · parts` evaluation units (`render3_cost`, `MARCH = 420`), bounded by `MAX_CHUNK_COST3 = 1,200,000,000` (a few seconds of one CPU core in the worst case, instead of the 8 M bound of the other kernels): a judge can always recompute one chunk, and a job cannot make a single chunk heavier than this. The full job is as expensive as its number of chunks: a 1080p image with 256 samples per pixel is 16 passes of 16 samples, 130,560 chunks.

**Parameters.** `RenderParams3{seed, width, height, spp, passes, bounces, fog0, fog1, cam, env, mats (≤ 24), parts (≤ 48)}`. All lengths are Q16.16 integers (65536 = 1.0) with coordinates `|v| ≤ 2²³`.
- **Parts** `Part3{geo, c, rot, op, mat, polar, mirror, off, group, shell}`. Geometry `geo`: `Sphere{r}`, `Ellipsoid{r[3]}`, `Box{h[3], rnd}` (rounded box, the rounding is part of `h`), `Cylinder{r, h, rnd}` and `Capsule{h, r}` (both along the local y axis), `Torus{big, small}`, `Cone{h, r1, r2}` (capped cone along y), `Plane` (half space `y < 0`). The point is first taken into the local frame, `q = rot · (p − c)` (`rot` is a 3×3 Q16 matrix, row-major, world to local), then `mirror` replaces `q.x, q.z` by their absolute values, then `polar = n ≥ 2` repeats the part `n` times around the local y axis (`k = ⌊(atan2(q.z, q.x) + sec/2) / sec⌋`, `sec = ⌊TAU/n⌋`, and `q.xz` is rotated by `−k·sec`), then `off` is subtracted, and `shell > 0` hollows the shape (`|d| − shell`). The distance formulas are those of the shaders of studio renderers: sphere `|q| − r`; ellipsoid `k0(k0−1)/k1` with `k0 = |q/r|`, `k1 = |q/r²|`; rounded box and cylinder `len(max(w,0)) + min(max(w),0) − rnd`; capsule `|q − (0, clamp(q.y,−h,h), 0)| − r`; torus `len(len(q.xz) − big, q.y) − small`; capped cone as in the reference code.
- **Minimum ellipsoid radius.** The ellipsoid distance squares `q / r²` in 64-bit integers. With a radius below **1/16 (`MIN_ELLIPSOID_R = 4096`)** the square overflows for the far points a ray visits (a march goes up to 60 units): the CPU wraps silently, but the CUDA compiler may assume that a signed overflow cannot happen and one GPU thread then loops forever (found on 2026-10-07 with a mint leaf 0.02 thick: a worker hung for minutes). `render3_validate` therefore refuses any ellipsoid with a radius under 4096, and `tests/gpu.rs::render3_refuses_ellipsoids_that_could_overflow` keeps it so. Thin leaves are made from a flatter but thicker ellipsoid, a box or a cylinder.
- **Combination.** `op` ∈ `Union`, `Smooth(k)` (polynomial smooth minimum, `h = clamp(½ + ½(b − a)/k, 0, 1)`, `b + (a − b)h − k·h(1 − h)`), `Sub` (`max(acc, −d)`), `Inter` (`max(acc, d)`), applied to the accumulator **of the part's group**; `group` is non-decreasing along the list (`autogroup` gives a part with `Smooth`/`Sub`/`Inter` the group of the part before it and starts a new group at every `Union`), and the groups are merged by a hard union. The material of a point is the one of the part that last lowered the accumulator.
- **Materials** `Mat3`: colours `alb`, `alb2` (sRGB bytes, squared to linear), `rough`, `metal`, `spec`, `emit` (Q10), `trans`, `glass` + `ior` (Q10) + `absorb` (Q10 per unit length), `coat`, a procedural texture `tex` ∈ 0..11 with parameters `tex_scale`, `tex_p`, `tex_q`, `tex_r`, and bump mapping `bump` / `bump_freq`. Textures: 1 checker (3-D cells), 2 stripes along axis `tex_p`, 3 value-noise mix of `alb`/`alb2`, 4 concentric rings, 5 wood grain, 6 angular sunburst (`sin(atan2·tex_p)` mixes the colours and the roughness), 7 bezel ticks (`|cos(atan2·tex_p)| > 0.985` inside a radial window, on upward faces). Added on 2026-10-07 for richer surfaces (all in integers, world space, bit-identical on the GPU, checked by the independent implementation and by the frozen vectors `scene3_textures`): **8 veined marble** (`tex_scale` = frequency, `tex_p` = how much a 4-octave noise warps the veins, `tex_q` = half width of a vein as a share of one stripe period; the stone `alb` is clouded toward the vein colour `alb2` by at most a quarter), **9 cracked cells** (Worley noise over the 27 neighbouring lattice cells: each cell mixes `alb` and `alb2` by its own hash scaled by `tex_q`, the borders, where the two nearest feature points are within `tex_p` of each other, are dark cracks that are also rougher), **10 swirl** (two colours mixed by a 4-octave noise whose coordinates are shifted by three more noises, `tex_p` = warp strength, with thin contour lines of the field, `tex_q` = number of lines), **11 floor tiles** on the xz plane (`tex_scale` tiles per unit, a tone per tile from a hash scaled by `tex_q`, dark rough grout of half width `tex_p` of a tile). `render3_validate` accepts `tex` up to 11. Scenes using them: `orb` (the Vearl Orb: liquid-metal sphere, textures 9, 10, 11) and `gallery` (the 3D scene: textures 3, 5, 8, 9, 10, 11). Noise is a 3-D value noise from an integer hash with a 3-octave or 5-octave fractal sum; `bump` perturbs the normal with the noise gradient. `atan2`, `sin` and `cos` are integer **CORDIC** routines (24 iterations, Q24 internals, constants in the source).
- **Environment** `Env3`: a sky gradient (`top`, `hor`, `gnd`, Q10 radiance), up to four **soft boxes** (`dir`, half sizes as tangents, `soft`, radiance), seen by every ray that leaves the scene after the first bounce; rays that leave the scene directly see the `bd_top`/`bd_bot` backdrop instead; `fog0`/`fog1` blend the first hit into the backdrop by a smoothstep of its distance.
- **Camera** `Cam3{pos, look, focal, aperture, focus}`: pinhole basis `fw = norm(look − pos)`, `rt = norm(cross(up, fw))`, `up' = cross(fw, rt)`, ray `norm(rt·u + up'·v + fw·focal)` with `u = (2sx − W)/H`, `v = −(2sy − H)/H`; with `aperture > 0` the origin moves on a disc of radius `aperture` (rejection sampling in a square, 8 tries) towards the point at distance `focus` along the pinhole ray (round bokeh).

**Random numbers.** PCG-style 32-bit hash; the stream of a sample is `pcg(px·1973 + py·9277 + chunk·26699 + s·612451 + seed₀)` then `pcg(· ⊕ seed₁)` (seed words = first 8 bytes of `seed`, little-endian); a draw is the top 16 bits (a Q16 fraction). The sub-pixel offset takes the first two draws; the lens, the sampling of the hemisphere, GGX half vectors and the Russian roulette use the following draws in the order of the code.

**Light transport.** Per sample: sphere tracing on `|d|` (so that rays travelling inside glass find the far side), step `0.9·|d|`, hit when `|d| < max(26·max(t, 0.3)/65536, 1)` (about 0.0004 relative), at most 420 steps and `t ≤ 60`; the normal is the 4-tap tetrahedral gradient (step 33). At each hit: emission is added; a black emitter ends the path; **glass** reflects with probability Fresnel (Schlick, `f0 = ((ior−1)/(ior+1))²`) or refracts (Snell, total internal reflection reflects), multiplies by `exp(−absorb·t)` while inside (squaring ladder for the exponential) and by the colour when entering; **clear coat** reflects with probability `(0.04 + 0.96(1−cos)⁵)·coat` through a GGX lobe (alpha 0.015); then specular reflection with probability `ps` (metals: always, throughput multiplied by the colour; dielectrics: throughput multiplied by `F/ps`), GGX half-vector sampling with `alpha = rough²` and `a = rough⁴` inside, else diffuse (cosine-weighted hemisphere by disc sampling, throughput `alb·(1−F)/(1−ps)`) or, with probability `trans`, a thin transmission; from the fourth bounce a Russian roulette terminates the path with probability `max(0.05, 1 − max(thr))` and reweights the survivors. Bias offsets along the geometric normal are 0.002 (0.0025 for glass, 0.004 for translucency).

**What the guarantee is.** Level 2: a sampling audit with a one-chunk fraud proof (§1, §7). A pass is a random walk estimate, deterministic given the seed: two honest workers produce the same bytes, and a worker that sends different bytes for any chunk is provably wrong. Noise is a property of the number of samples, not an error.

**Measured** (RTX 5060 Ti and the 30 CPU cores of the same server, 2026-10-06, development measurements): the complete watch scene at 960×544 with 64 samples per pixel renders in 18.2 s on the GPU and 39.0 s on the CPU, with byte-identical output; at 1280×720 and 128 samples per pixel in 63 s on the GPU. The GPU gain is about 2× on this branchy 64-bit workload.

## 5. Cost bounds (protection against denial of service)

Judging a fraud proof forces **all nodes** to recompute a chunk. The cost per chunk is therefore **bounded at submission**: Monte Carlo `samples·(instructions + dim)`, rendering `256·spp·(48 + 6 + 24 + 2)·primitives`, all `≤ MAX_CHUNK_COST = 8,000,000` units (of the order of a few milliseconds per chunk on CPU: measured 0.62 s for the 256 tiles of a 256×256 image, spp 2, 4 primitives, i.e. 2.4 ms per tile). Number of chunks ≤ 1024 (≤ 8192 for Render2, §4 bis; ≤ 262,144 for Render3, §4 ter, whose chunk bound is 1.2 G units), output ≤ 4096 bytes, ≤ 8 pending data requests.

## 6. Transactions (bincode encoding, `docs/07` §2)

`TxKind::L2` = `u32` tag **15**, then `L2Tx` (`u32` tag; a `Submit` carries a `Kernel`: `MonteCarlo` 0, `Render` 1, `Render2` 2, `Render3` 3): `Submit` 0 `{kernel, chunks u32, escrow u64, deadline u64}` · `Claim` 1 `{job_id}` · `Post` 2 `{job_id, root}` · `Accept` 3 · `Fetch` 4 `{job_id, chunk u32}` · `Serve` 5 `{job_id, chunk, out Vec<u8>, path}` · `SlashUnserved` 6 · `Fraud` 7 `{job_id, chunk, out, path}` · `Settle` 8.
`Kernel`: `MonteCarlo` 0 `McParams` · `Render` 1 `RenderParams`; `Prim`: `Sphere` 0 `{c [i32;3], r i32, col [u8;3]}` · `Plane` 1 `{y i32, col, col2}` · `Box` 2 `{c, h, col}`. `job_id = H("vearl/l2/v1", client, nonce u64, bincode(kernel), chunks u32 LE)`.

State rules: those of the market (`docs/07` §11.3) — `Submit` (`escrow ≥ MIN_ESCROW`, valid kernel, `deadline > height`, 10 % burn), `Claim` (10 % bond), `Post`, `Accept`, `Fetch`/`Serve`/`SlashUnserved`, `Settle` (window closed and no pending request; expired `Open`/`Claimed`) — with, for `Fraud`, the verification of §2 (`Posted` job, window open, valid Merkle opening, chunk **different** from the recomputation).

## 7. Threat model specific to level 2

| threat | handling | guarantee |
|---|---|---|
| worker falsifies a fraction φ of the chunks | the client recomputes `m` randomly drawn chunks; any wrong chunk is provable by anyone | detection with probability `1 − (1−φ)^m` (φ = 5 %, m = 12 out of 64 chunks: 46 %; m = 64: 100 %). **A single falsified chunk is only seen with probability m/N.** |
| profitability of cheating | gain = cost avoided (≈ φ of the work); expected loss = detection probability × bond (10 % of the price) | deterrent only if `P(detection)·bond > φ·cost`; **no demonstrated economic guarantee** `[HYPOTHESIS]` |
| worker withholds the outputs | on-chain `Fetch`, `SlashUnserved` | a requested chunk is served or the worker is sanctioned |
| worker serves an output inconsistent with its root | Merkle opening refused; the client then cannot prove the fraud on-chain and must refuse to accept | the client is never paid by force: `Settle` pays the worker **after** the window if the client does not react — **the client must audit before the end of the window** |
| malicious client (never accepts) | `Settle` by anyone after the window | the worker is paid |
| client accuses wrongly | the chain recomputes the chunk: "correct chunk" → refusal | impossible |
| fraud proof costly to judge (DoS) | cost per chunk bounded at submission (§5) | bounded |
| **client + worker collusion** | — | outside the model (a client can choose not to check) |
| **the kernel itself wrong** (implementation bug) | second implementer (§8) | verified on 18 chunk outputs; `[AUDIT ACTION]` |
| **inexact but undetected result** | — | **possible**: this is the nature of a sampling audit. Do not use this level for a result that requires absolute exactness. |

**The verifier's dilemma**: security rests on someone recomputing. Here that someone is the client (who has an interest in exactness) or any third party holding the outputs; the protocol does **not** reward third-party auditors other than through half of the bond in case of proven fraud `[LIMIT]`.

## 8. Verification (measured)

- `tests/l2.rs` (9 tests): exact integer semantics of the machine (root, saturation, rounding, selection), estimation of π, deterministic and non-trivial rendering, validation bounds (program, registers, tiles, cost), honest life cycle (Accept and settlement through the window), **fraud proven with a single chunk** (Monte Carlo and rendering), false accusations and forged proofs refused (correct chunk, false opening, path of another chunk, indices out of bounds, window closed), availability (Fetch/Serve/SlashUnserved), expiry, monetary-supply invariant.
- `tests/net.rs::level2_…`: on **real nodes** (Noise network): honest worker paid (Monte Carlo and rendering), cheating worker (`--cheat-l2`) sanctioned at the index of the falsified chunk.
- **Kernels verified by a second implementation**: `tools/l2_ref.py`, written from §3–4 (Python integers, no floating point), reproduces **byte for byte** 18 chunk outputs of the Rust node (3 Monte Carlo programs including saturation and square root, 3 rendering scenes with spp 1, 2 and 3); vectors frozen in `tests/vectors/l2-kernels-v1.json` (test `level2_kernel_vectors_are_frozen`).
- Demonstration: `vearl-cli l2-submit … render 128 128 2 7` then `l2-finish … 12 image.ppm`: an image assembled from 64 tiles computed by the worker, each opened against the root, 12 recomputed locally. `render2` instead of `render` submits the Render2 scene. **Render3**: `vearl-cli l2-submit NODE KEY ESCROW render3 SCENE WIDTH HEIGHT SPP PASSES SEED` (`SCENE` = `watch`, `mini` or `cocktail`), then the same `l2-finish` (it fetches the chunks on 16 connections at once and assembles the image with `render3::assemble`). The same scenes can be rendered locally without a network with `vearl-l2 render3 SCENE W H SPP PASSES out.ppm [gpu]`. On a `--gpu` worker the chunks go to the card by batches sized so that one launch takes about 0.6 s (a display GPU on Windows kills a kernel that runs more than about 2 s).
- **Render3 speed** (RTX 4070 SUPER, Windows, shared with two miners, 2026-10-07, development measurements): 128 × 128 pixels at 32 samples per pixel (512 chunks of 4 samples) in **0.9 s** for the cocktail scene and 0.4 s for the watch; one 16-sample chunk takes 0.1 s on one CPU core, so the sampling audit of 4 chunks is cheap. A job of 256 chunks (cocktail, 128 × 128, 64 samples) went through the demo chain in about 2.5 minutes, of which the audit and the transfer of the 256 chunks took 32 s: nearly all of the rest is waiting for blocks.
- **Render2 speed** (RTX 5060 Ti, 30 CPU cores of the same server, 2026-10-06, development measurements): a full-HD frame (1920×1088, 8,160 tiles, 2 bounces) in **2.00 s on the CPU and 0.45 s on the GPU** at 1 sample per pixel, and in **0.89 s on the GPU at 4 samples per pixel**; the two 1 sample images are byte-identical. A 240-frame orbit film at 4 samples per pixel took 170.9 s (0.71 s per frame). The GPU is about 4× faster than 30 cores on this branchy 64-bit integer workload, not 100×: the point of the GPU port is that a worker can render HD frames in under a second while any CPU node can still judge a one-tile proof.
- **Render2** (§4 bis): `tools/l2_ref.py` reproduces byte for byte the tiles of 4 scenes (8 chunks, spp 1 to 3, 0 to 2 bounces, with and without floor, glow and blending) of `tests/vectors/l2-kernels-v1.json`; the GPU port gives bit-identical tiles for every tile of 4 scenes (`tests/gpu.rs`).

## 9. Limits and next steps

- **Several miners and the waiting queue.** A worker holds at most `--max-jobs` level-2 jobs at once (default 1: claimed and not yet published). A busy worker leaves the other open jobs to the other miners; each worker looks at the queue in its own order (a hash of the job and of its key), so two miners facing the same queue do not all race for the same job, and a claim that lost the race is dropped at once instead of blocking that worker for 30 s. The computation of a job (all chunks and the Merkle tree) runs in a background thread: the node keeps validating blocks, relaying transactions and serving chunks during a render of several minutes (before, it was frozen). Test: `level2_a_busy_worker_leaves_the_queue_to_the_other_miners` (two workers, four jobs). **Not done:** a job that a worker claimed and never published expires and the worker is slashed, but the job is not reopened for another miner (protocol change, to decide).

- The kernels are **canonical on CPU**. Render2 and Render3 also have GPU implementations (`gpu/vearl_render2.cu`, `gpu/vearl_render3.cu`, used by a `--gpu` worker) that give identical outputs (tests `gpu_render2…`, `gpu_render3…`); Monte Carlo and the first rendering kernel run on the CPU cores only. On the branchy Render3 workload the GPU is only about 2× faster than 30 CPU cores (development measurement).
- **Cost of judging a fraud proof.** A node that judges a `Fraud` transaction recomputes one whole chunk. For Render3 the bound is `MAX_CHUNK_COST3` (1.2 × 10⁹ evaluation units); a typical studio scene at 32 samples per pass takes about 0.3 s on one core, a deliberately adversarial scene (rays that never escape, 14 bounces, many parts) can take several seconds. Consensus therefore allows **at most `MAX_L2_FRAUD_PER_BLOCK` = 8 fraud proofs per block** (`src/chain.rs`, test `a_block_may_carry_only_a_few_level_two_fraud_proofs`); the others wait for the next block. The worst case adversarial scene has not been measured systematically `[TO MEASURE]`.
- Render3 procedural textures are evaluated in **world space** (no local-space textures yet), and an image rendered with few samples is noisy: production-quality stills need hundreds of samples per pixel, i.e. many passes (minutes on a GPU, not a second).
- No streaming generation of chunks: the worker computes everything before publishing; the node computes under a lock (up to a few seconds at the maximum cost) `[TO IMPROVE]`.
- No public-randomness audit (the draw of the chunks to check is left to the client); no k-of-n replication; no payment of third-party auditors; no pricing at real cost (the minimum escrow is the same for any job).
- No general kernel (virtual machine), no floats, no stateful simulation (molecular dynamics, fluids): this requires deterministic computation with checkpoints and interactive bisection `[RESEARCH]` (`docs/05`, P10e).
- No load test and no external audit of level 2.
